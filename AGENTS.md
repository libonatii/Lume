# Lume — instruções para agentes e colaboradores

Antes de propor ou alterar comportamento do produto, leia nesta ordem:

1. [Regras de negócio consolidadas](docs/REGRAS_DE_NEGOCIO.md) — fonte única de verdade do produto, do estado v3, da política de XP v2, da Agenda, da importação e do que foi aposentado das versões v1/v2.
2. [Estado atual e pendências de implementação](docs/IMPLEMENTACAO.md) — mapa do que já funciona × o que falta implementar ou verificar em produção.
3. [Aplicativo de desktop](companion/README.md) e [Publicação e CI](docs/RELEASE.md), antes de mexer no pacote Electron (`companion/`) ou no workflow de release.
4. [Extensão do navegador](extension/LEIAME.md), antes de mexer na captura de cursos em `extension/` ou nos provedores em `public/providers/`.

Esses documentos descrevem o estado atual e as regras vigentes do Lume. Prevalência: instrução explícita da pessoa responsável > `docs/REGRAS_DE_NEGOCIO.md` > código e testes antigos. Mantenha a documentação enxuta e coerente com novas decisões.

## Comandos

Windows com ExecutionPolicy restrita: `npm.ps1`/`npx.ps1` falham; use `npm.cmd`/`npx.cmd` ou `node` direto.

```sh
npm run dev          # Astro em 4321 + API Node em 4173; LUME_API_PORT troca a API e o proxy acompanha
npm start            # build + serve dist/ em 4173 (PORT ajusta)
npm run preview      # só serve o dist/ existente
npm run build        # astro build + scripts/headers.mjs (gera dist/_headers com CSP)
npm test             # node --test nos arquivos listados em package.json
node --test tests/unit/auth.test.js
node --test --test-name-pattern="redefini" tests/unit/session.test.js
npm run test:e2e     # Playwright; exige dist/ e sobe o próprio servidor na 4187
npx playwright test tests/e2e/session.spec.js --project=desktop
```

Não há lint, typecheck, formatter nem TypeScript configurados — não invente `npm run lint`/`tsc`. O projeto é JavaScript puro (`.js`/`.jsx`), `"type": "module"`, Node >= 22.23.4 (usa `node:sqlite`).

No CI, `PLAYWRIGHT_CHANNEL=bundled` força o Chromium baixado; localmente o padrão é o Chrome instalado.

## Arquitetura que não é óbvia pelos nomes

### Persistência direta da biblioteca (revisão de 03/11/2026)

- A conta usa `GET /api/library` e `POST /api/library/actions`, com operações por entidade, revisão otimista e idempotência; `api/domain/library-store.js` grava `materials`, `units`, `study_progress`, `study_tasks`, `study_sessions` e `account_documents` (esquema `0012_library.sql`). Materiais têm somente `units` no domínio, API v3 e banco. Listas/árvores são visualizações derivadas por `material-model.js`.
- Não reintroduza IndexedDB, fila offline, sincronização por cursor ou reconciliação de documentos no navegador. A prévia dura só na página aberta. Não há migração de dados: documentos antigos no servidor (`user_state`) são preservados como arquivo, nunca convertidos, e a conta entra com uma biblioteca nova e vazia (`ensureLibrary`); leituras compartilhadas devolvem estado nulo para eles. Backups só aceitam v3. Clientes antigos recebem `client_outdated` ao tentar gravar sobre uma biblioteca nova.
- Conclusões, conquistas e tempo elegível são preparados no servidor e gravados no mesmo batch da biblioteca (`library-actions.js`, `library-time.js`). A revisão aborta o batch inteiro em conflito. Repetir usa o mesmo id de operação; conflito pede recarga, sem mescla automática. `outbox.js` e `useProgressSync.js` foram removidos.
- As telas recebem ações nomeadas de `src/features/{account,library,plan,progress,settings}/actions.js`; `act` e o setter ficam privados em `useLume`. Cada ação aplica a regra de `public/` sobre o estado mais recente e devolve `null` quando a gravação está bloqueada: preserve o formulário e não anuncie sucesso. Telas e domínios leem `materialSteps`, `materialStructure` e `materialLesson`; o cache pressupõe objetos imutáveis. Não grave `steps`, `structure` ou `selection` em materiais. Biblioteca e diálogo usam `nextAction` do roteiro.
- `useLume` compõe `features/account/useAccountSession.js` (sessão e prévia), `features/library/useLibraryPersistence.js` (estado, revisão, envios serializados em memória e repetição) e `features/progress/useXp.js` (leitura do livro). O transporte e a aplicação genérica de regras ficam privados nessa composição, sem acesso pelas telas.
- **PDFs e disciplinas (11/11/2026):** disciplinas são a coleção `subjects` (`subject.put/delete/order`, tabela `study_subjects`, regras em `public/subject-domain.js`); materiais ganham `subjectId`. PDF anexado é material `type: 'pdf'` com `pdf` (metadados, sumário) e `reading` (página), uma etapa única, regras em `public/pdf-domain.js`. O arquivo vai por `PUT /api/library/files/:id` para R2/`data/media` (`api/domain/library-files.js`, cota em `library_files`, plano em `storage_plans`); nunca guarde o PDF no navegador. `library-actions.js` recusa material que aponte para arquivo inexistente e apaga o objeto ao excluir o material. O leitor usa `pdfjs-dist` carregado sob demanda (`src/features/library/pdf-client.js`); o worker é `.mjs` e precisa ser servido como JavaScript. IA só em `POST /api/library/identify`, sob pedido. Detalhes em [Regras de Negócio](docs/REGRAS_DE_NEGOCIO.md#4-biblioteca-materiais-unidades-e-disciplinas-estado-v3).
- Estilos por funcionalidade ficam em `src/features/<área>/*.css`, e a casca em `src/app/shell.css`. O Redesign Sereno (telas do Stitch "Lume Academy Design System") acrescenta `today.css`, `shelf.css`, `focus.css`, `schedule-session.css` e `welcome.css` ao fim de `lume.css`; peças comuns (`.soft-badge`, `.crest-card`, `.metric-label`) ficam em `80-redesign-moderno.css`. Ritmo semanal e minutos por dia vêm de `minutesByDay`/`weeklyRhythm` em `public/session-domain.js`. `src/styles/` mantém tokens, base, shader, diálogos, responsividade e tema. `src/styles/lume.css` importa tudo em ordem explícita; não acrescente imports nos componentes alterando a cascata por ordem de montagem.

- **SPA em uma única página Astro.** `src/pages/index.astro` monta `<App client:only="react" />` e define o service worker. As rotas são hashes resolvidos em React (`#hoje`, `#biblioteca`, `#plano`, `#agenda`, `#foco`, `#agendar`, `#aplicativo`, `#amigos?convite=`, `#perfil?id=`; `#conheca` é a apresentação pública, aberta sem conta como `#recuperar`) — criar tela é componente + uma linha na tabela `src/app/routes.jsx` (hash, título, seção e aba), não arquivo em `src/pages/`. O menu tem quatro destinos (`SECTIONS` com `nav` diferente de `false`: Início, Biblioteca, Plano de Estudos e Amigos; a tela Início é a antiga Hoje e mantém o hash `#hoje`, porque `#inicio` é o onboarding), num cabeçalho em vidro (barra fixa inferior no celular; o cabeçalho não pode ter `backdrop-filter` no celular, senão prende a barra). A seção Perfil (`nav: false`) abre pelo menu da conta, com as abas Meu perfil, Conquistas e Configurações. As abas de seção e o título da janela derivam da tabela; uma aba pode ter ícone (`tabIcon`). Plano de Estudos reúne Agenda (`#plano`), Calendário (`#agenda`) e Tarefas; essas três telas desenham as abas abaixo do próprio cabeçalho (`hideTabs` na rota e `<SectionTabs/>` na tela), como no Stitch. `#foco` e `#agendar` pertencem a Hoje e ao Plano sem aba própria. Endereços antigos viram apelidos (`ALIASES`): `#missoes` e `#roteiro` abrem o Plano, `#historico` abre Conquistas. `#missoes` é alias de `#roteiro` (`ALIASES`). `src/app/App.jsx` resolve a rota e os diálogos (`src/app/modals.jsx`); telas ficam em `src/features/<área>/` e componentes visuais em `src/ui/`. Para gravar, use a ação nomeada da funcionalidade; não exponha setters do estado inteiro às telas. Recursos compartilhados (amigos, ranking, colaboração, não lidas, conversas, Desktop) passam por `useResource` (`src/lib/resources.js`), com cache, revalidação ao montar e intervalo compartilhados. O estado do cliente passa por `src/app/useLume.js` e as chamadas HTTP por `src/lib/api.js`. Estilo em `src/styles/` (um arquivo por seção, importados em ordem por `src/styles/lume.css`).
- **Agenda:** leia [Regras de Negócio §8](docs/REGRAS_DE_NEGOCIO.md#8-agenda-calendário-e-lembretes-publicagenda-domainjs) antes de alterar calendário, recorrência ou lembretes. `public/agenda-domain.js` guarda regras; `agenda_entries` persiste ocorrências com referências às tarefas existentes. `appointment.put/delete/order` usa o batch da biblioteca. Lembretes são reivindicados uma vez por conta por `POST /api/agenda/reminders`, com revisão transacional e tabela `agenda_reminders`. A Agenda não entra no perfil social. Encerrar atividade não conclui tarefas nem gera XP; recorrência não repete recompensa de aula. Notificações exigem site/app executando e rede; no Electron, preservar `backgroundThrottling: false` para a janela minimizada. Verificação nativa: `node scripts/test-agenda-desktop.mjs` (build e dependências de `companion/` necessários; conta e configuração isoladas).
- **Calendário interativo:** FullCalendar Standard 7 em `features/agenda/Agenda.jsx`; CSS externo no manifesto `lume.css`, cores por tokens. `calendar-model.js` converte instantes para o fuso original ao arrastar; datas sem horário permanecem civis. No mês, arrastar escolhe apenas o dia e remove o horário do bloco (`calendarPatch(..., { month: true })`). O motor visual não persiste nem gera recorrência. `saveAppointment` grava checklist e compromisso juntos; falha de gesto abre o editor, série exige escopo antes de gravar. Semana inicial no computador, dia no celular. Nada acima da grade pode mudar de altura depois de montada (avisos flutuam): o FullCalendar guarda posições e o arrasto quebraria. Mover e excluir oferecem Desfazer pelo `notify(message, { action })` de `App.jsx`.
- **Regras de domínio ficam em `public/*.js`** (`domain.js`, `material-model.js`, `progress-domain.js` — registro único de progresso do estado v3, `import-domain.js`, `session-domain.js`, `study-plan.js`, `companion-domain.js`, `profile-domain.js`, `tasks-domain.js`, `slides-domain.js`, `subject-domain.js`, `pdf-domain.js`, `agenda-domain.js`, `settings-domain.js`, `backup-domain.js`, `merge-domain.js`, `xp-policy.js`, `schedule-domain.js` — cronograma derivado de `state.plan` e do progresso). O React (`src/`) e o Node as importam do mesmo arquivo; não duplique regra em `src/lib`.
- **A API é um app só (`api/`), com dois adaptadores:** `api/app.js` monta a tabela de rotas (`api/routes/*.js`), e cada rota declara método, caminho, se exige conta (`auth`), checagem de origem (`origin`) e limite de tentativas (`rateLimit`). `server.js` (Node + `node:sqlite`, estáticos de `dist/`) e `worker.js` (Cloudflare + D1 + R2) só adaptam banco (`api/adapters/sqlite.js`, `api/adapters/d1.js`, contrato `{ run, first, all, batch }`), imagens e variáveis; não contêm regra de rota. Erros de domínio estendem `AppError` (`api/errors.js`) e viram `{ error, code, field? }` num só lugar. Regras ficam nos módulos compartilhados: `api/domain/auth.js`, `api/domain/progress.js`, `api/domain/rewards.js`, `api/domain/commands.js`, `api/domain/import-server.js`, `api/domain/companion.js`, `api/domain/friends.js` (inclui o perfil entre amigos), `api/domain/xp.js` (livro `xp_events` e ranking), `api/domain/state.js` (estado com revisão otimista), `api/domain/messages.js`, `api/domain/collaboration.js`, `api/domain/email.js` (Resend; sem configuração, o link de redefinição só vai para o log), `api/domain/media.js` (avatar/header em R2 no Worker via `env.MEDIA`, `data/media/` no Node) e `public/*-domain.js`. O teste `tests/unit/api-contract.test.js` roda o mesmo roteiro HTTP no Node e no Worker (`wrangler dev` local).
- **XP validado no servidor:** os valores vigentes ficam em `public/xp-policy.js` (`XP_VALUES`, `LEVEL_XP`, blocos de tempo, teto diário). O cliente atual usa `/api/library/actions`; `library-actions.js` avalia `RULES` de `rewards.js` e grava progresso, XP e conquistas no mesmo batch. `library-time.js` prepara o tempo elegível para esse batch, e `library-subtasks.js` o XP de subtarefa concluída (10 XP uma vez por subtarefa, teto de 50 XP/dia). O horário do cliente só pode atrasar uma conclusão. `api/domain/xp.js` guarda o livro `xp_events`, correção e ranking. `/api/progress` e `/api/xp/complete|bonus|slides|time` são compatibilidade para contas não convertidas; contas convertidas recebem `client_outdated`. O saldo legado continua separado, fora do nível novo e do ranking.
- **`server.js` aplica todos os `migrations/*.sql` no boot** (`applyMigrations` em `api/adapters/sqlite.js`), em ordem alfabética; para D1 é `npx wrangler d1 migrations apply lume --remote`. Nunca edite migração já aplicada — crie o próximo número.
- **O servidor lê `dist/` e o CSP uma única vez ao iniciar**; depois de `npm run build`, reinicie `server.js` para servir a versão nova.
- **Estado:** a API entrega v3 com materiais/unidades. Progresso é só `state.progress` (origem e `revertedAt`); use `isCompleted`/`completedUnitIds`, nunca listas paralelas. `restoreState` valida v3 por material/registro e recusa versões anteriores. O cliente não persiste estudo em localStorage. Revisão conflitante pede recarga. A tarefa em foco na Hoje é o campo de conta `focusTaskId` (regras em `tasks-domain.js`; `restoreState` descarta foco em tarefa concluída ou inexistente). `backup-domain.js` permite mesclagem explícita de arquivo v3, não sincronização entre dispositivos.
- **Cores são tokens com função** em `src/styles/00-tokens.css`, por paleta (`html[data-palette="moderno"|"variante2"]`, exibidas como Azul e Roxo) e por tema (`data-theme`): `--action` botão principal, `--lume` destaque e navegação, `--mint` progresso, `--success`, `--reward` XP/sessão em âmbar, `--warning`, `--danger`, `--xp-from`/`--xp-to` para a barra de XP. Não use cor fixa em componentes; misture tokens com `color-mix`. Espaçamento usa `--space-1`…`--space-6` e `--actions-gap`; campos em linha usam `.form-grid` (não `.field-row`, que fica só para rótulo + ação). Mensagens de validação usam `.form-error` (e `.form-error-block` para falhas de gravação com repetição); não crie `auth-error` ou variações locais. `--logo-bg` e as cores do SVG em `Logo` (`ui.jsx`) não mudam com a paleta: o logo é preservado por decisão da responsável. A folha é empacotada pelo Astro (nome com hash), então não há `?v=` manual; a ordem dos `@import` em `src/styles/lume.css` é a ordem da cascata — não reordene sem conferir as telas.
- **CSP é hash exato** do `<script>`/`<style>` inline que o Astro emite em `dist/index.html` (`scripts/headers.mjs`). `script-src` não tem `'unsafe-inline'`: script inline injetado em runtime é bloqueado. `style-src-attr 'unsafe-inline'` libera só atributos `style`.
- **Service worker (`public/sw.js`)** usa stale-while-revalidate em assets da mesma origem (menos navegação e `/api/*`): quem já visitou vê a versão em cache uma vez e a atualização só aparece na visita seguinte. Ao alterar CSS/imagens locais, teste com service worker limpo.

## Armadilhas de configuração

- As variáveis têm o mesmo nome no Node e no Worker (`api/config.js`): `SHOW_RESET_LINK` (em `wrangler.jsonc` é `"false"`), `ATTEMPT_LIMIT`, `BCRYPT_ROUNDS`. `LUME_SHOW_RESET_LINK` e `LUME_ATTEMPT_LIMIT` continuam aceitos como apelidos no servidor local.
- IA de organização é opcional e só no servidor: `LUME_AI_API_KEY` (fallback `OPENAI_API_KEY`), `LUME_AI_BASE_URL`, `LUME_AI_MODEL`. Sem chave, o organizador determinístico responde. Nunca exponha a chave no frontend nem em arquivos versionados.
- `ATTEMPT_LIMIT` vale 10 por padrão nos dois ambientes e limita cadastro, login e recuperação; importação (30), convites (20), colaboração (30) e mensagens têm limite próprio por rota. Os e2e usam 1000 (a suíte cadastra mais de 200 contas em 10 minutos) e o teste de contrato usa 200.
- `BCRYPT_ROUNDS=6` no Worker é um compromisso com o limite de 10 ms de CPU do Workers Free e fica abaixo do mínimo 10 da OWASP. Não aumente sem medir (`node scripts/benchmark-auth.mjs 6`); a medição em produção continua pendente.
- Senhas novas: bcrypt até 72 bytes UTF-8, sem truncamento. Hashes PBKDF2 legados são preservados e migram só na redefinição de senha.
- `data/` é local e ignorado no Git (`data/lume.db` guarda as contas); não apague nem versione. Os e2e usam `data/e2e-<timestamp>`.

## Aplicativo de desktop (pacote `companion/`)

O aplicativo de desktop **é o Lume completo numa janela Electron**, com bandeja, presença opcional e atualização; presença não é o propósito dele. "Companion" é só o nome técnico (pasta, tags, endpoints). Em textos de produto, chame de "Lume" ou "aplicativo de desktop". Pacote npm separado em `companion/` (Electron + electron-builder, lockfile próprio): `npm install --prefix companion` uma vez; `npm run companion:app` abre a janela/bandeja e `npm run companion` roda o agente de terminal. `lume.cmd` na raiz é o iniciador. Configuração do usuário em `%APPDATA%\Lume\companion.json`, fora do repositório. `npm test` inclui `companion/update.test.js`; o CI também roda `node --check` nos arquivos do Companion. Release: suba `companion/package.json` e crie a tag `companion-v<versão>` — se não bater, o workflow falha. Detalhes em [Publicação e CI](docs/RELEASE.md); o que falta implementar está em [Funcionalidades pendentes](docs/IMPLEMENTACAO.md).

## Extensão do navegador (`extension/`)

Extensão MV3 com um passo de build: o leitor de curso, que o usuário aciona na página da plataforma (`activeTab`), é escrito em `extension/src/capture.js` (ESM, importa o registro de provedores) e `npm run extension:build` (esbuild) gera `extension/capture.js`, script clássico versionado porque a pasta é carregada como está no Chrome; `tests/unit/extension-build.test.js` falha se o gerado estiver desatualizado. Nunca edite `extension/capture.js` à mão. O leitor devolve o formato de `normalizePayload` com `extraction.kind: 'extension-capture'` e `completionSource: 'lesson-flags'`; o Lume recebe por `postMessage` (`src/lib/extension.js`, ouvinte em `App.jsx`) e abre a revisão do `ImportCourse`. Não há endpoint novo. **Cada plataforma é um provedor** em `public/providers/<id>.js`, listado em `public/providers/registry.js` (única lista de domínios do código): declara capacidades (`syllabus`, `progress`, `resume`, `requiresLogin`), como reconhecer o curso pelo endereço (`identify`) e os leitores que tem (`readers.page` na extensão; `public`/`snapshot` no servidor). Provedor novo é um arquivo novo + uma linha no registro. Hoje só o Gran tem leitor próprio (`readers.page`: rotas JSON da página, só `GET`, uma aula do Gran por aula, com `externalId`); as demais usam a leitura de tela da extensão e o leitor de página compartilhado do servidor. Fonte desconhecida não lê marcas de concluído. Aula com `externalId` tem id independente do título; na reimportação, aulas antigas mantêm o id e ganham o `externalId` (`adoptExistingIds` em `import-domain.js`). Conclusões lidas na primeira importação são histórico sem XP; só leituras posteriores, confirmadas na revisão, viram `origin: 'integration'` (`observedCompletionIds` em `applyCourseImport`). Testes em `tests/e2e/capture.spec.js` (páginas de exemplo, não reais). Instalação e limites em [extension/LEIAME.md](extension/LEIAME.md). Em scripts Python de edição, não escreva a barra invertida dupla seguida de b em strings comuns: vira backspace.

## Publicação

`npx wrangler deploy` executa `npm run build` antes e envia `dist/` (Worker + D1). Site de referência: <https://lumeacademy.site>. Publicar não é conclusão de tarefa: não faça deploy, migração remota ou release sem pedido explícito.

## Contexto obrigatório do produto

- Lume é uma plataforma social de estudos: biblioteca, continuidade de materiais, amigos, mensagens diretas, compartilhamento de aprendizados, colaboração, conquistas e placares de estudo.
- Comunidades, servidores, canais e grupos estão fora do escopo desta etapa. O social se limita a amigos, mensagens diretas entre amizades aceitas e colaboração em projetos; não reintroduza grupos por causa de documentação antiga.
- Cadastro e login com e-mail e senha são requisitos do Lume, assim como recuperação de acesso e saída da conta. A prévia local é temporária; não descreva como decisão de que o produto não terá login ou senha.
- A gamificação deve reconhecer avanço real: estudo efetivo, aula concluída, leitura concluída, curso concluído e entrega de projeto. Não premiar cliques ou movimentação na interface.
- Abrir uma janela, entrar no site, cadastrar um material, preparar a mesa, abrir uma aula, conectar uma conta, pausar ou enviar mensagens não gera XP.
- Apoios para começar e dividir uma tarefa continuam úteis, mas não são automaticamente eventos de recompensa. Não confundir preparação com conclusão de estudo.
- Tarefas não têm XP próprio. Concluir tarefa vinculada conclui a aula e usa sua recompensa validada no servidor uma única vez; sem vínculo, 0 XP. Disciplina completa concede 200 XP e conquista. Cargos são só títulos, sem bloquear funcionalidades.
- A inclusão de pessoas neurodivergentes é central. Personalização, conforto visual e pausas sem punição devem conviver com uma gamificação substancial e uma experiência social opcional.
- Não reduza o produto a um organizador individual de microtarefas, nem retire amigos ou placares por presumir que competição nunca pode ser inclusiva.
- O ranking é um recurso central obrigatório, com classificações por nível acumulado, cursos distintos concluídos e empenho no período. O recorte inicial é de amigos; não há ranking de grupos nesta etapa. Não o substitua apenas por um placar semanal de XP. Participação configurável não torna o desenvolvimento do ranking dispensável.
- Nenhum registro de atividade deve ser descrito como prova de compreensão, inteligência ou benefício clínico.
- O look and feel, os ícones e os textos da aplicação não devem ter nenhuma relação com "sustentabilidade", ecologia ou metáforas botânicas (não use termos como "sustentável", "cultivar", nem ícones como `sprout`, `leaf` ou `tree`). Use vocabulário direto de estudo: ritmo constante, ritmo equilibrado, construir o hábito e continuidade.

## Regras para implementar

- Preserve os dados existentes. A migração dos eventos antigos exige tratamento explícito; não apague progresso nem converta preparações antigas em aulas concluídas. O modelo legado em execução (5 XP por preparação, 10 XP por etapa, 10 XP por tarefa de prova, nível a cada 100 XP) não é a nova política e não pode alimentar ranking compartilhado.
- Separe recursos implementados, simulações locais e funcionalidades planejadas. A prévia sem conta e uma simulação de login no navegador não são autenticação. A API local já valida credenciais e emite sessão; isso não comprova publicação nem verificação do mesmo fluxo em produção. A sincronização de uma cópia do estado não equivale à validação de XP no servidor.
- Integrações devem declarar suas capacidades. Não prometa rastreamento automático de qualquer URL, videoaula, PDF, artigo ou repositório.
- Não coloque credenciais de integrações no frontend, em arquivos versionados ou em saídas de ferramentas. Não publique o conteúdo de repositórios privados por padrão.
- A atribuição de XP da versão com contas deve ser validada no servidor, com eventos identificáveis e proteção contra repetição. O navegador não deve ser a autoridade de um placar compartilhado.
- A lista de tarefas vive em `public/tasks-domain.js`; `library-actions.js` também aplica a conclusão vinculada no servidor. Reabrir tarefa não desfaz aula. Cargos permanecem nas pausas e são reavaliados nas correções. Atualize testes e `docs/REGRAS_DE_NEGOCIO.md` ao mudar essas regras.
- Os valores vigentes de balanceamento estão em `public/xp-policy.js` e documentados em `docs/REGRAS_DE_NEGOCIO.md`. Não espalhe valores contraditórios entre telas e regras de domínio.
- Ao mudar uma regra de produto, atualize os documentos afetados e os testes relevantes. Testes do protótipo não são justificativa para conservar uma regra já substituída.
- Ao receber tarefa só de documentação, documente as divergências; não aproveite para migrar dados, ativar serviços, alterar a pontuação ou publicar mudanças funcionais.
- Textos de interface, documentação e comentários: português do Brasil.

## Verificação e entrega

`npm test` para regras de domínio/autenticação; `npm run build` para validar a aplicação; `npm run test:e2e` para fluxos de interface afetados (rode o build antes, porque o Playwright serve `dist/`). O script `test` lista os arquivos um a um em `package.json`: ao criar um teste em `tests/unit/*.test.js`, inclua-o lá, senão ele não roda no CI. Módulos de servidor ficam em `api/domain/`; testes que precisam de banco usam `applyMigrations` e `sqliteAdapter` de `api/adapters/sqlite.js`. Os e2e rodam com 1 worker (`fullyParallel: false`) porque compartilham o SQLite — não paralelize. A análise de link no e2e é interceptada por rota (simulação); extração real de plataformas não é exercitada. Mudanças apenas em documentação exigem revisão de coerência e links, sem repetir testes de código inalterado. Por decisão explícita da responsável, a interface não oferece modo essencial nem tratamento de movimento reduzido; os campos antigos permanecem apenas para compatibilidade dos dados.

Na entrega, informe o que mudou, o que foi verificado e o que ainda não está implementado. Não chame um recurso de concluído com base apenas em sua aparência.
